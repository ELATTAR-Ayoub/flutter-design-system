# Elattar v0.0.1 file layout — plain-language map

This is the readable map of the branch currently being worked on:

```text
codex/v0.0.1-el-cli-registry
```

The branch exists locally. Its changes are intentionally still uncommitted
because the checkout already contained a large documentation worktree that
must not be silently reset, stashed, or mixed into an unsafe commit.

## The seven folders that matter

```text
flutter-design-system/
├── lib/                   The real Flutter design system
├── example/               The documentation website and live showroom
├── registry/              The catalog of files the CLI may install
├── packages/elattar_cli/  The CLI that installs those files into another app
├── test/                  Package and release-contract tests
├── tool/                  Registry, icon, and visual-verification tools
└── docs/                  Plans, research, and release records
```

Think of it as a supply chain:

```text
lib/ source → registry/ catalog → elattar CLI → consumer Flutter app
       └──────── example/ documents and demonstrates the same APIs
```

## What was structurally renamed

```text
old validation-rule filename  → lib/src/components/ui/validation_rule.dart
old safe-area filename        → lib/src/components/ui/safe_area.dart
old validation-rule CLI slug  → rule
old safe-area CLI slug        → safe-area
old suffixed wordmark         → ELATTAR
```

Public Dart APIs now use `El*`. There are no compatibility aliases for the
rejected prefix because version `0.0.1` has not been published. The lowercase
`el(...)` spacing helper remains because it is the spacing scale, not a
component-name prefix.

## What the CLI writes into a consumer app

Running:

```console
elattar init
elattar add button
```

creates a consumer-owned structure like this:

```text
consumer-app/
├── elattar.yaml            Project-level Elattar CLI configuration
├── .elattar/
│   └── manifest.json       Installed-item and file-hash record
├── lib/
│   ├── components/ui/       Installed component source and ui.dart barrel
│   └── design_system/
│       ├── foundation/      Installed token source
│       ├── foundation.dart  Foundation barrel
│       ├── effects/         Transitive effect source when required
│       └── motion/          Transitive motion source when required
├── assets/elattar/          Installed fonts and textures when required
├── shaders/                 Installed shader resources when required
└── pubspec.yaml             Updated asset, shader, font, and dependency entries
```

Running `elattar add --all` installs every user-facing component plus the
foundation, effects, motion, assets, and shaders reached through dependency
resolution.

## The practical rule

- Build and edit components in `lib/`.
- Demonstrate them in `example/`.
- Describe how they are delivered in `registry/`.
- Let `packages/elattar_cli/` copy them into a consumer project.
- Do not place product screens inside `lib/src/components/`.
- Do not hardcode colors, typography, spacing, radii, shadows, or motion in
  `lib/` or `example/lib/`; use the foundation tokens and public `El*` APIs.
