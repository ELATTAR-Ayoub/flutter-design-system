# v0.0.1 — Task 12, the owner's runbook

Every step here is one only you can take. They are ordered so that nothing
irreversible happens before the thing it depends on is live and verified.

Read the whole thing once before starting step 1. Two of these steps cannot be
undone.

---

## Before you start

Three preconditions. If any is false, stop.

| Check | How |
| --- | --- |
| Tasks 10 and 11 (local half) are done and green | The consumer verification report exists and says which commands were actually run |
| CI is green on the exact commit you will tag | Actions tab, the push run for that SHA — not a PR run for a different SHA |
| The working tree is clean and pushed | `git status --porcelain` prints nothing; `git log origin/public-release-v0.0.1..HEAD` is empty |

---

## Step 1 — Make the repository public

**Reversible.** You can make it private again, though anything cloned in the
meantime stays cloned.

GitHub → repository **Settings** → **General** → **Danger Zone** → *Change
repository visibility* → **Public**.

Then verify from a logged-out context, not from your own browser session:

```bash
curl -s -o /dev/null -w "%{http_code}\n" https://api.github.com/repos/ELATTAR-Ayoub/flutter-design-system
```

`200` means public. It returned `404` at every check through Task 9.

**Why first:** everything downstream assumes a public repository. The registry
`sourceLink`s, the plugin install commands on `/skills`, and the clone URLs in
the README are all unreachable until this is done.

---

## Step 2 — Decide what `main` should be

You have a choice, and it has a real consequence.

All 99 registry `sourceLink` values now point at
`https://github.com/ELATTAR-Ayoub/flutter-design-system/blob/**v0.0.1**/…`,
not at `main`. So the tag alone makes every source link work — **you do not
have to merge to `main` for the release to be correct.**

What merging to `main` still buys you: anyone landing on the repository's
default branch sees the released state rather than a months-old tree. That is
a real thing for a first public release, and `main` is currently far behind.

Either fast-forward `main` to this branch, or open a PR and merge it. If you
merge, re-run CI on the merge commit and tag **that** commit in step 3.

---

## Step 3 — Create and push the tag

**Irreversible in practice.** A pushed tag can be deleted, but anything that
already fetched it has it, and re-pointing a tag at different content is the
exact failure the immutable registry exists to prevent. Treat it as permanent.

Confirm you are on the commit CI went green on:

```bash
git log --oneline -1
```

Then:

```bash
git tag -a v0.0.1 -m "Elattar v0.0.1 — first public release"
git push origin v0.0.1
```

The tag name is not cosmetic: `packages/elattar_cli/lib/src/identity.dart`
defines `releaseTagFor`, and `version_identity_test.dart` asserts the format
matches. `v0.0.1`, exactly.

---

## Step 4 — Deploy Pages

**Reversible.** You can redeploy.

GitHub → **Actions** → **Deploy Docs** → *Run workflow*. Leave
`stage_registry` checked and `registry_version` as `0.0.1`.

That workflow builds the docs, then stages the registry into the same artifact
at `/registry/0.0.1/`. It refuses to overwrite a published version with
different bytes, so re-running it later is safe and a change of content is a
loud failure rather than a silent replacement.

Verify **both** halves, unauthenticated:

```bash
curl -s -o /dev/null -w "docs        %{http_code}\n" https://elattar-ayoub.github.io/flutter-design-system/
curl -s -o /dev/null -w "index.json  %{http_code}\n" https://elattar-ayoub.github.io/flutter-design-system/registry/0.0.1/index.json
curl -s https://elattar-ayoub.github.io/flutter-design-system/registry/0.0.1/release.json
```

The last one should print the version, schema version, item count, file count,
tree hash and the commit it was generated from. If `index.json` 404s, **stop**
— publishing the CLI now would ship a command that cannot fetch anything.

## Step 5 — Hand back for the live verification

This is where the agent picks Task 11 up again: the clean-cache install from
the real public URL, from a machine with no repository credentials. Let that
finish before step 6.

It is the only test that exercises what an actual stranger will experience,
and it is cheap compared to what step 6 costs if it is wrong.

---

## Step 6 — Publish `elattar_cli`

**Irreversible. A published version cannot be replaced, edited or unpublished.**

Re-check the name is still free, then review the archive one last time:

```bash
curl -s -o /dev/null -w "%{http_code}\n" https://pub.dev/api/packages/elattar_cli   # expect 404
cd packages/elattar_cli
dart pub publish --dry-run
```

Read the file list. It should be 26 files, ~47 KB, with no `test/`, no
`pubspec.lock`, no `.dart_tool/`, and 0 warnings. Then:

```bash
dart pub publish
```

You will be asked to authenticate with the Google account that will own the
package. Whichever account you use becomes the publisher — pick the one you
want owning this long-term, not whichever is already signed in.

---

## Step 7 — Prove the real thing works

From a clean machine, or at minimum an empty cache:

```bash
dart install elattar_cli
cd $(mktemp -d) && flutter create demo && cd demo
elattar init --foundation source
elattar add button
elattar doctor
flutter analyze
```

No `--registry` flag anywhere. If that sequence works, the release is real.

---

## Step 8 — GitHub release

Create the release from the `v0.0.1` tag, with notes taken from the `0.0.1`
section of `CHANGELOG.md`. Do not rewrite them there — that file is the single
source of truth and the site renders it.

---

## Step 9 — Turn on the automation

Only now:

- Restore an automatic Pages trigger in `.github/workflows/pages.yml` (the
  gate comment at the top lists what had to close first — most of it already
  has; the remaining items were repository visibility and the tag, which
  steps 1 and 3 closed).
- Set up pub.dev automated publishing, which requires the package to be linked
  to the GitHub repository. This only works after a first manual publish,
  which is why it is last.

## If something goes wrong

| Symptom | What it means | What to do |
| --- | --- | --- |
| `index.json` 404s after a Pages deploy | The registry was not staged into the artifact | Re-run the workflow with `stage_registry` checked |
| Staging fails with "Refusing to overwrite" | The registry content changed but the version did not | This is the guard working. Publish `0.0.2`, do not force it |
| `dart pub publish` rejects the package | Read the message — it is usually a metadata or size rule | Fix, commit, re-run `--dry-run` until 0 warnings |
| `elattar` installs but `add` fails | The registry endpoint is not reachable | `elattar doctor` reports which registry it tried and whether it answered |
| A source link 404s | The tag is missing, or points elsewhere | Check `git ls-remote --tags origin` |

**The one ordering rule:** never publish the CLI before the registry endpoint
is live. An installable command that cannot retrieve its payload is not a
usable release, and the CLI version is the thing you cannot take back.
